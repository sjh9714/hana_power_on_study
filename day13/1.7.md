# langchain-chroma란?

`langchain-chroma`를 이해하는 가장 좋은 방법은 자바(Java)나 C++ 같은 객체 지향 프로그래밍에서 쓰이는 **인터페이스(Interface)와 구현체(Implementation)의 개념**으로 접근하는 것입니다.

이 관점에서 보면 `langchain-chroma`와 `chromadb`의 관계가 매우 명확해집니다.

---

## 1. 인터페이스 관점에서의 구조 분석

랭체인(LangChain) 프레임워크는 수많은 종류의 벡터 DB(Chroma, Milvus, Pinecone, FAISS 등)를 다루어야 합니다. 이 DB들은 만든 회사도 다르고, 내부 언어(C++, Go, Python 등)도 다르며, 데이터를 넣고 빼는 함수명(`add`, `insert`, `query`, `search`)도 제각각입니다.

이 문제를 해결하기 위해 랭체인은 `VectorStore`라는 추상 인터페이스(추상 클래스)를 미리 정의해 두었습니다.

### 1) 랭체인의 공통 인터페이스: `VectorStore` (Interface)

모든 벡터 DB는 랭체인 생태계에 들어오려면 다음과 같은 표준 메서드(인터페이스 규격)를 구현해야 합니다.

* `add_documents(documents)`: 문서를 저장하는 표준 메서드
* `similarity_search(query, k)`: 유사도 검색을 수행하는 표준 메서드
* `as_retriever()`: LLM 파이프라인에 연결할 수 있는 검색기 객체로 변환하는 표준 메서드

### 2) 실제 데이터베이스 엔진: `chromadb` (Engine)

인터페이스와는 상관없이 독자적인 규격과 자신만의 고유한 C++ 기반 인덱싱 엔진(`hnswlib`)을 가지고 작동하는 **순수 데이터베이스 실체**입니다.

### 3) 인터페이스 구현체: `langchain-chroma` (Implementation)

바로 이 `langchain-chroma` 패키지가 랭체인의 `VectorStore` 인터페이스를 상속받아 크로마DB의 기능을 호출하도록 구현한 '실제 구현체(Concrete Class)'입니다.

내부 코드는 대략 아래와 같은 구조의 어댑터 패턴으로 디자인되어 있습니다.

```python
# langchain-chroma의 내부 개념적 구조 예시
from langchain_core.vectorstores import VectorStore
import chromadb # 실제 순수 엔진 임포트

class Chroma(VectorStore): # 랭체인 인터페이스 상속
    def __init__(self, client):
        self._client = client # 순수 chromadb 클라이언트 보관
        
    def add_documents(self, documents):
        # 랭체인의 표준 호출을 크로마DB 고유 문법인 .add()로 통역
        raw_texts = [doc.page_content for doc in documents]
        self._client.add(documents=raw_texts, ...)
        
    def similarity_search(self, query, k):
        # 랭체인의 표준 검색 호출을 크로마DB 고유 문법인 .query()로 통역
        results = self._client.query(query_texts=[query], n_results=k)
        return 변환된_랭체인_Document_리스트

```

## 2. 인터페이스 기반 설계가 주는 결정적 장점: "결합도 낮추기"

애플리케이션을 개발할 때 `langchain-chroma`라는 인터페이스 구현체를 사용하면 다형성(Polymorphism)의 이점을 그대로 누릴 수 있습니다.

만약 프로토타입 단계에서는 가벼운 **ChromaDB**를 쓰다가, 상용 서비스로 전환하면서 억 단위의 데이터를 처리하기 위해 대형 분산 DB인 **Milvus**나 **Qdrant**로 데이터베이스를 전면 교체해야 하는 상황이 왔다고 가정해 보겠습니다.

### ❌ 순수 DB API (`chromadb`)로 짰을 때의 문제점

코드 전반에 `collection.add()`, `collection.query()` 같은 크로마DB 전용 메서드가 파묻혀 있기 때문에, DB를 바꾼다면 소스 코드의 비즈니스 로직을 처음부터 끝까지 다 뜯어고쳐야 합니다.

### 인터페이스 기반 (`langchain-chroma`)으로 짰을 때의 이점

코드의 핵심 로직(RAG 파이프라인, LLM 연결부)은 부모 인터페이스인 `VectorStore` 규격(`similarity_search` 등)으로 작성되어 있습니다. 따라서 개발자는 **주입(Injection)하는 구현체 클래스**만 슬쩍 바꿔 끼우면 됩니다.

```python
# 1. 크로마DB를 쓸 때
from langchain_chroma import Chroma
vector_store = Chroma.from_documents(docs, embeddings)

# 2. 만약 Milvus로 바꾸고 싶다면? 상단 선언부 2줄만 변경
from langchain_milvus import Milvus
vector_store = Milvus.from_documents(docs, embeddings)

# 3. 비즈니스 로직은 인터페이스 규격을 따르므로 한 줄도 고치지 않습니다.
# 어떤 DB 구현체가 들어오든 동일하게 작동합니다.
relevant_docs = vector_store.similarity_search("검색어", k=3)

```

## 3. 요약

* **`chromadb`**: 나만의 독자적인 문법과 기능을 가진 백엔드 데이터베이스 엔진
* **`VectorStore`**: 랭체인이 선언해 둔 벡터 DB 제어용 표준 인터페이스
* **`langchain-chroma`**: `VectorStore` 인터페이스의 명세에 맞춰 `chromadb` 엔진을 돌리도록 구현해 놓은 **'표준 컴포넌트 부품'**

`langchain-chroma`는 파이썬의 대표적인 AI 프레임워크인 랭체인(LangChain)에서 벡터 데이터베이스인 크로마DB(ChromaDB)를 쉽고 유기적으로 사용할 수 있도록 연결해 주는 공식 패키지(통합 커넥터)입니다.

## 4. 간단한 워크플로우 예시

동일한 문서를 데이터베이스에 넣고 유사도 검색을 하는 과정을 두 라이브러리가 어떻게 다르게 표현하는지 비교해 보면 이해가 더 쉽습니다.

### 1) `langchain-chroma` 방식 (랭체인 규격 표준 문법)

>파일명 : step10.py

```python
# pip install langchain-chroma langchain-community langchain-core sentence-transformers
# 1. 랭체인과 크로마DB 임포트

from langchain_chroma import Chroma
from langchain_core.documents import Document
from langchain_community.embeddings import HuggingFaceEmbeddings

# 1. 임베딩 모델 정의 (HuggingFace의 오픈소스 모델 활용)
# 앞서 chromadb가 내부적으로 다운로드했던 'all-MiniLM-L6-v2' 모델을 랭체인 규격으로 선언합니다.
# 이 모델 역시 로컬 캐시에 저장되므로 외부 API 비용이 들지 않습니다.
# `HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")`는 랭체인(LangChain)을 사용할 때 문장을 AI가 이해할 수 있는 좌표(벡터)로 바꾸기 위해 선언하는 **로컬 실행형 임베딩 모델 부품**입니다.
#자바나 C++의 객체 지향 관점으로 보면, 이 코드는 랭체인의 **`Embeddings` 인터페이스를 구현한 HuggingFace 전용 어댑터 클래스의 인스턴스를 생성하는 과정**입니다.
embedding_model = HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")

# 2. 데이터 준비 (랭체인 규격인 Document 객체 형태로 변환)
# 텍스트 내용(page_content)과 메타데이터(metadata)를 하나의 객체로 묶습니다.
raw_documents = [
    "파이썬을 활용한 머신러닝과 딥러닝 실무 가이드. 데이터 전처리부터 모델 배포까지 다룹니다.",
    "자바 스프링 부트 기반의 엔터프라이즈 웹 애플리케이션 아키텍처 및 백엔드 개발.",
    "쿠버네티스와 도커를 이용한 마이크로서비스 아키텍처 구축 및 Devops 인프라 실무.",
    "시간 흐름에 따른 데이터 분석과 LSTM, RNN 기반의 시계열 딥러닝 예측 모델링.",
    "맛있는 이탈리아 파스타 요리 레시피와 토마토 소스 숙성 비법 가이드."
]

metadatas = [
    {"category": "AI/Data", "year": 2025},
    {"category": "Backend", "year": 2024},
    {"category": "DevOps", "year": 2026},
    {"category": "AI/Data", "year": 2026},
    {"category": "Cooking", "year": 2023}
]

# List Comprehension을 사용하여 Document 객체 리스트 생성
docs = [
    Document(page_content=text, metadata=meta) 
    for text, meta in zip(raw_documents, metadatas)
]

# 3. 크로마DB 생성 및 데이터 인덱싱 (VectorStore 인터페이스 구현체 사용)
# 기존 PersistentClient와 collection 설정을 from_documents() 메서드 하나로 통합 처리합니다.
print(">> 데이터를 벡터 데이터베이스에 인덱싱하는 중...")
vector_store = Chroma.from_documents(
    documents=docs,
    embedding=embedding_model,
    collection_name="book_recommendation",
    persist_directory="./my_langchain_db"  # 로컬 영구 저장 경로
)
print(">> 인덱싱 완료!\n")


# 4. 유사도 검색 수행 (VectorStore 표준 인터페이스 활용)
query_text = "컨테이너 기반의 클라우드 배포 인프라를 공식 공부하고 싶어"

print(f"🔍 유저 질문: '{query_text}'")
print("-" * 50)

# 구조화된 유사도 검색 호출 (가장 유사한 상위 2개 문서 요청)
# 검색 결과로 랭체인의 Document 객체와 거리(Distance) 점수가 튜플 형태로 반환됩니다.
results = vector_store.similarity_search_with_score(query_text, k=2)

# 5. 결과 출력
for i, (doc, score) in enumerate(results):
    print(f"[순위 {i+1}] (거리 점수: {score:.4f})")
    print(f"카테고리: {doc.metadata.get('category')} / 발행년도: {doc.metadata.get('year')}")
    print(f"내용 요약: {doc.page_content}")
    print("-" * 50)
```

## 5. 요약: 언제 어떤 것을 써야 할까요?

* **순수 `chromadb`를 써야 할 때:**
* 랭체인(LangChain) 프레임워크를 사용하지 않는 프로젝트일 때
* 가볍고 직관적인 자체 파이썬 서비스나 API 서버에 벡터 검색 기능을 이식할 때
* 크로마DB 고유의 세부적인 세팅(인덱스 파라미터 튜닝 등)을 직접 통제해야 할 때


* **`langchain-chroma`를 써야 할 때:**
* 이미 프로젝트 메인 아키텍처로 **LangChain 프레임워크를 도입**하여 RAG(검색 증강 생성)나 AI 에이전트를 구축하고 있을 때
* PDF나 웹페이지 문서들을 랭체인의 `DirectoryLoader`, `TextSplitter` 등으로 파싱한 후, 연속적으로 DB에 바로 밀어 넣고 싶을 때
* 향후 서비스 규모가 커지면 대형 기업용 벡터 DB(Milvus 등)로 확장할 가능성이 열려있을 때

## 6. 주요 변경점 및 인터페이스 관점의 설명

### 1) 데이터 구조의 변화 (`Document` 객체화)

* **기존 `chromadb`:** `documents=[...]`, `metadatas=[...]` 형식을 각각의 리스트 배열로 분리하여 인덱싱 메서드에 던졌습니다.
* **`langchain-chroma`:** 랭체인의 표준 데이터 포맷인 `Document(page_content=..., metadata=...)`라는 캡슐화된 객체 리스트를 넘겨받습니다. 랭체인 생태계 내의 다른 모듈(텍스트 파서, 로더 등)과 완벽하게 호환을 이루기 위함입니다.

### 2) 명시적인 임베딩 주입 (`embedding=embedding_model`)

* 순수 크로마DB는 내부에 임베딩 코드가 숨겨져 자동 처리되었지만, 랭체인 인터페이스 규격은 "어떤 임베딩 모델을 사용할 것인지"를 명시적으로 주입받도록 설계되어 있습니다.
* 덕분에 나중에 모델을 OpenAI의 API나 다른 경량화 모델로 바꾸고 싶을 때 `embedding_model = OpenAIEmbeddings()` 형태로 한 줄만 교체하면 하위 인덱싱 로직을 건드릴 필요가 없습니다.

### 3) 메서드의 추상화 및 직관화

* **기존 검색 방식:** `collection.query()`를 통해 딕셔너리 구조(`results['documents'][0]`) 내부의 기괴한 다중 인덱스 루프를 돌며 데이터를 파싱해야 했습니다.
* **변경 검색 방식:** `vector_store.similarity_search_with_score()` 메서드를 호출하면 **`(Document, score)` 형태의 깔끔한 튜플 리스트**를 반환하므로 결과 데이터 가공 및 출력이 훨씬 직관적이고 표준화됩니다.

### 4) 인터페이스 관점에서의 활용도

랭체인 아키텍처 내에서 HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2") 코드가 가지는 가장 큰 장점은 "교체의 유연성"에 있습니다.

```python
# 1. 로컬에서 무료로 가볍게 검증할 때는 이 모델을 주입
embedding_model = HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")

# 2. 향후 대규모 엔터프라이즈 서비스로 전환하여 정확도를 극대화하고 싶다면?
# 하위 코드(ChromaDB 적재, 검색 등)는 단 한 줄도 바꾸지 않고 상단 선언만 교체
from langchain_openai import OpenAIEmbeddings
embedding_model = OpenAIEmbeddings(model="text-embedding-3-small")

```

HuggingFaceEmbeddings 클래스를 사용하여 작성된 코드를 OpenAIEmbeddings 클래스, model은 text-embedding-3-large을 사용하게 변경된 코드입니다.

앞단 선언만 변경되고 전제적인 코드는 변경되지 않았습니다.
이것이 인터페이스(wrapper, LangChain)의 좋은 점입니다

```python
    for text, meta in zip(raw_documents, metadatas)
]

# 4. 크로마DB 생성 및 데이터 인덱싱
print(">> 데이터를 벡터 데이터베이스에 인덱싱하는 중...")
vector_store = Chroma.from_documents(
    documents=docs,
    embedding=embedding_model,
    collection_name="book_recommendation_openai",  # 모델이 바뀌었으므로 컬렉션 이름을 새로 지정하는 것이 좋습니다.
    persist_directory="./my_langchain_openai_db"    # 새로운 DB 저장 경로
)
print(">> 인덱싱 완료!\n")


# 5. 유사도 검색 수행
query_text = "컨테이너 기반의 클라우드 배포 인프라를 공식 공부하고 싶어"

print(f"🔍 유저 질문: '{query_text}'")
print("-" * 50)

results = vector_store.similarity_search_with_score(query_text, k=2)

# 6. 결과 출력
for i, (doc, score) in enumerate(results):
    print(f"[순위 {i+1}] (거리 점수: {score:.4f})")
    print(f"카테고리: {doc.metadata.get('category')} / 발행년도: {doc.metadata.get('year')}")
    print(f"내용 요약: {doc.page_content}")
    print("-" * 50)

```

즉, `HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")`는 "비용 부담 없이 내 컴퓨터 자원만 사용하여, 랭체인 규격에 맞는 고성능 텍스트-벡터 변환 엔진 인스턴스를 하나 만들겠다"라는 선언으로 이해하시면 됩니다.

## 8. OpenAI 추천 임베딩 모델 2종

### 1) text-embedding-3-small (최고의 가성비 및 일반 목적용)

* **기본 차원 수:** 1536 차원
* **특징:** 성능과 인프라 효율성 사이에서 최고의 밸런스를 자랑하는 모델입니다. 이전 세대(ada-002) 대비 영어 작업 벤치마크(MTEB) 성능이 향상되었을 뿐만 아니라, 가격이 **5배나 저렴**해졌습니다.
* **추천 대상:** 대규모 문서를 처리해야 하거나 가성비가 중요한 일반적인 검색, 추천 시스템, RAG 아키텍처 구축 시 기본 모델로 가장 먼저 추천됩니다.

### 2) text-embedding-3-large (최고 성능 및 높은 정밀도 요구용)

* **기본 차원 수:** 3072 차원
* **특징:** OpenAI가 제공하는 가장 강력한 최상위 임베딩 모델입니다. 다국어 검색 벤치마크(MIRACL) 점수가 크게 향상되어, **한국어를 포함한 비영어권 텍스트 및 다국어 교차 검색**에서 압도적인 정밀도를 보여줍니다.
* **추천 대상:** 복잡한 도메인 지식(의학, 법률, 금융 등)의 맥락을 정밀하게 구분해야 하거나 최고 수준의 검색 정확도가 최우선인 시스템에 추천됩니다.

---

### 2. `text-embedding-3` 시리즈의 핵심 혁신 기능: 가변 차원 (Native Dim Shortening)

이 최신 모델들이 기존 모델들과 구별되는 결정적 차이점은 **개발자가 출력 벡터의 차원 수를 마음대로 줄일 수 있도록(가변 차원) 설계**되었다는 점입니다.

기본적으로 `large` 모델은 3072차원을 뱉어내지만, API 호출 시 `dimensions` 파라미터를 지정하면 **256, 512, 1024차원 등으로 압축하여 출력**할 수 있습니다.

* **이점:** 벡터 DB(`ChromaDB`, `Milvus` 등)에 저장할 때 차원 수가 작을수록 메모리와 저장 공간이 획기적으로 절약되고 검색 속도가 빨라집니다.
* OpenAI의 인덱싱 아키텍처 특성상 차원을 줄여도 핵심 의미 보존 능력이 매우 뛰어납니다. (예컨대 `large` 모델을 1024차원으로 줄여서 사용해도, 줄이지 않은 기존 1536차원의 `ada-002`보다 성능이 더 우수합니다.)

---

### 3. 선택 가이드

* **비용 절감과 속도가 최우선이라면?** ➡️ `text-embedding-3-small`을 선택하세요.
* **글로벌 다국어 지원 및 미세한 문맥적 정확도가 최우선인가요?** ➡️ `text-embedding-3-large`를 선택하세요.
* **벡터 DB의 사양 제한이나 인프라 비용 부담이 있는가요?** ➡️ **`text-embedding-3-large`를 선택한 뒤 1024나 512차원으로 줄여서 사용**하는 전략이 아주 훌륭한 대안이 됩니다.

## 9. OpenAI 임베딩 모델 비용

**OpenAI의 3세대 임베딩 모델 제품군(`text-embedding-3-small`, `text-embedding-3-large`)을 사용하려면 비용이 발생됩니다.** 앞서 실습했던 `HuggingFaceEmbeddings`나 크로마DB의 내장 모델은 내 컴퓨터(로컬)의 CPU/GPU 자원을 사용하여 연산하기 때문에 100% 무료였지만, OpenAI의 모델은 **클라우드 API 방식**이기 때문에 요청한 텍스트의 양만큼 비용이 청구됩니다.

과금 방식과 실제 비용이 어느 정도 인지 알려드리겠습니다.

---

### 1. 과금 방식: 토큰(Token) 기준 요금제

OpenAI는 글자 수가 아니라 토큰(Token)이라는 언어 단위로 비용을 계산합니다. 대략적으로 영어는 1단어가 약 1.3토큰, **한국어는 문맥에 따라 1글자가 1~2토큰** 정도로 계산됩니다.

요금은 100만 토큰(1M Tokens)을 기준으로 책정되어 있으며, 3세대 모델의 가격은 다음과 같습니다.

| 모델명 | 100만 토큰당 가격 (USD) | 한화 환산 (약 수치) | 특징 |
| --- | --- | --- | --- |
| **`text-embedding-3-small`** | **$0.02** | 약 26원 | 극도로 저렴함 (ada-002 대비 1/5 가격) |
| **`text-embedding-3-large`** | **$0.13** | 약 170원 | 높은 정확도 대비 합리적인 가격 |

---

### 2. 실제 체감 비용은 어느 정도일까요?

숫자만 보면 감이 잘 안 오실 수 있으니, 현실적인 프로젝트 규모로 시뮬레이션을 해보겠습니다.

> 💡 **체감 예시 (`text-embedding-3-small` 기준):**
> * **A4 용지 1장** 분량의 텍스트는 대략 1,000 ~ 1,500 토큰입니다.
> * 즉, **A4 용지 약 700~1,000장** 분량의 방대한 텍스트 데이터를 통째로 벡터 DB에 인덱싱(저장)해도 **단돈 26원($0.02)** 정도만 청구됩니다.
> * 사용자가 질문을 던질 때(유사도 검색) 발생하는 쿼리 토큰은 기껏해야 수십 토큰 미만이므로, 검색할 때 드는 비용은 거의 0원에 수렴합니다.

이처럼 OpenAI의 GPT-4 같은 LLM 생성 모델(100만 토큰당 수 달러~수십 달러)에 비하면 **임베딩 모델의 비용은 거의 공짜에 가까울 정도로 극도로 저렴한 편**입니다.

---

### 3. OpenAI API 사용을 위한 결제 구조

OpenAI API는 사용한 만큼 후불로 내는 방식이 아니라, 개발자 계정에 최소 $5(약 6,500원) 이상의 크레딧을 미리 충전(Pre-paid/Top-up)해두고 카드가 자동 결제되도록 연동하는 구조입니다.

처음 카드를 등록하고 $5를 충전해 두면, 개인 프로젝트나 프로토타입 개발 단계를 진행하는 수개월 동안 잔액이 다 떨어지지 않을 정도로 넉넉하게 쓸 수 있습니다.

---

### 4. 로컬 무료 모델 vs OpenAI 유료 모델 선택 요약

* **비용 0원, 보안 최우선, 오프라인 개발 환경:** ➡️ 기존에 사용하셨던 `HuggingFaceEmbeddings`(로컬 MiniLM 모델) 조합을 계속 사용하시는 것이 좋습니다.
* **한국어/다국어 검색 품질 극대화, 대규모 서비스 운영, 모델 관리 귀찮음:** ➡️ 커피 한 잔 값($5)을 충전하더라도 OpenAI의 `text-embedding-3` 시리즈를 API 인터페이스로 연결하여 쓰는 것이 훨씬 강력한 성능을 발휘합니다.

## 10. 구글(Google)에서 제공하는 고성능 인공지능 임베딩 모델 제품군

구글의 임베딩 생태계는 자사의 거대언어모델 브랜드인 **지미나이(Gemini)** 아키텍처에 기반을 두고 있으며, 구글 클라우드의 **버텍스 AI(Vertex AI)** 플랫폼이나 개발자용 **구글 AI 스튜디오(Google AI Studio)** API를 통해 개발자들에게 제공됩니다.

현재 구글이 주력으로 밀고 있는 핵심 임베딩 모델들과 그 특징을 알아보겠습니다.

---

### 1. 구글의 대표 임베딩 모델 제품군

구글은 크게 **텍스트용** 모델과 이미지·텍스트를 모두 다루는 **멀티모달용** 모델로 나누어 제공합니다.

구글 임베딩을 사용해 서비스를 빌드할 때 사실상 유일하고 강력한 선택지인 `gemini-embedding-001`은 다음과 같은 압도적인 스펙을 자랑합니다.

* **가변 차원 출력 (Matryoshka Embeddings):** 벡터의 차원 수를 **128차원부터 최대 3072차원까지** 개발자가 자유롭게 조절할 수 있습니다. 중요한 점은 차원을 줄여도 핵심 정보의 손실이 매우 적어, 성능을 크게 떨어뜨리지 않으면서 데이터베이스 저장 용량과 검색 비용을 드라마틱하게 아낄 수 있습니다.
* **작업 유형(Task Type) 최적화:**
임베딩을 생성할 때 이 벡터를 어디에 쓸지 구글 API에 힌트를 줄 수 있습니다. 이 기능 덕분에 하나의 모델로 전천후 성능을 냅니다.
    * `RETRIEVAL_DOCUMENT`: 검색 대상이 될 지식 베이스 문서용 임베딩
    * `RETRIEVAL_QUERY`: 사용자의 질문 검색어용 임베딩
    * `SEMANTIC_SIMILARITY`: 문장 간 유사도 비교용
    * `CLASSIFICATION` / `CLUSTERING`: 분류 및 군집화용

* **압도적인 다국어 처리와 긴 문맥:**
한국어를 포함한 100개 이상의 다국어 벤치마크 점수가 이전 세대 대비 비약적으로 상승했으며, 최대 **2,048 토큰**의 긴 텍스트 입력값을 한 번에 임베딩할 수 있습니다.

### 2. 비용 및 요금 체계 (OpenAI와의 비교)

구글 역시 클라우드 API 기반의 **유료 모델**입니다. 다만 과금 기준이 토큰(Token)인 OpenAI와 달리, 구글 Vertex AI는 글자 수(Characters)를 기준으로 요금을 책정하는 독특한 방식을 씁니다. (공백 제외 문자 수 기준)

* **가격 표준:** 텍스트 임베딩 기준으로 **100만 글자(1M Characters)당 약 $0.025** 수준입니다.
* **비용 체감:** 한글은 보통 1글자가 1~2토큰으로 잡히기 때문에, 토큰 기준인 OpenAI와 비교했을 때 **전체적인 비용은 OpenAI 3-small 모델과 거의 비슷하거나 아주 미세하게 저렴한 편**에 속합니다. 부담 없이 프로토타이핑을 돌릴 수 있는 가성비입니다.
